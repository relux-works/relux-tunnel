# Author threat model and user-facing security claims

## Description
Complete the existing seed threat model and publish the bounded user-facing security claims contract that downstream disclosure, privacy, diagnostics, and policy work must consume. Reconcile claims against current architecture, ADRs, routing/DNS, relay, update, CI, and Keychain boundaries; distinguish implemented evidence, planned mitigations, residual risk, and explicit non-goals.

## Scope
In scope: audit and update .spec/threat-model.md; add a shippable claims source document under .spec; enumerate assets, data flows, adversaries, trust boundaries, mitigations, residual risks, abuse boundaries, non-goals, and change control; include a does-hide/does-not-hide matrix and claim-to-source crosswalk; verify consistency with .spec/architecture.md, .spec/security-privacy.md, .spec/routing-dns-lifecycle.md, .spec/relay-protocol.md, .spec/platform-distribution.md, and accepted ADRs; attach a task-scoped outcome and validation evidence. Out of scope: legal approval, App Store submission copy approval, new product behavior, runtime implementation, telemetry introduction, marketing claims not supported by evidence, external penetration testing, or secrets/user traffic in artifacts.

## Acceptance Criteria
1. .spec/threat-model.md is no longer a seed and covers all named assets, adversaries, data flows, trust boundaries, mitigations, residual risks, abuse boundaries, non-goals, and change-control triggers for macOS-first v1. 2. A separate shippable security-claims source gives plain-language approved and prohibited claims, including that SSH metadata remains visible and fingerprintable, the exit host sees destination metadata and plaintext, Relux Works is not in the baseline path, and fail-closed is platform-scoped rather than absolute. 3. Every positive claim is traced to an accepted ADR/spec and current implementation evidence or explicitly labeled planned/unverified; no planned mitigation is presented as shipped behavior. 4. The threat model and claims are internally consistent with the named source specs, contain no secrets or user traffic, and pass repository formatting, link/reference, board, and privacy checks. 5. A TASK-ID-scoped outcome records the claim crosswalk, changed files, validation commands, residual open evidence, and downstream consumers; a fresh independent Codex reviewer accepts the work before done.
