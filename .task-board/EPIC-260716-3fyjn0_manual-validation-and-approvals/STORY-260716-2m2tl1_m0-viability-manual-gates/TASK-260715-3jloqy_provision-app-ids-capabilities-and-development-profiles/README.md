# Provision the macOS App IDs, capabilities, and development profiles

## Description
Create exactly four macOS App IDs in the Relux Works Apple Developer account - works.relux.tunnel.mac, works.relux.tunnel.mac.tunnel, works.relux.tunnel.probe.mac and works.relux.tunnel.probe.mac.tunnel - enable the Network Extensions capability on all four, hosts included, and generate one Mac Development profile per App ID with this Apple-silicon Mac registered. Apple requires the packet-tunnel entitlement on the containing app as well as the embedded provider, so host App IDs are provisioned exactly like provider App IDs. No App Group record is created and the App Groups capability is enabled on nothing: rule G4 of the approved matrix (TASK-260715-ypo7yo) withholds com.apple.security.application-groups from every macOS target. There is no Keychain access-group portal mutation to perform at all, because keychain sharing has no portal record and rule K2 withholds keychain-access-groups from every macOS target. The human authorization for these mutations is granted once in Ceremony C1 (TASK-260728-q5kjta); this task is performed unattended by the agent using that granted session, and the human does not wait for it. Preserve reproducible non-secret metadata and validate each downloaded profile against the approved matrix. The four iOS identifiers stay defined in the matrix and are not provisioned on this path because iOS is deferred under ADR-024. If the portal forces a fresh two-factor challenge mid-run, record it as a named short re-authentication interaction rather than silently retrying.

## Scope
In scope: Apple Developer portal mutations for exactly the four approved macOS identifiers; the Network Extensions capability on all four, hosts included; development certificates selected by authorized operators; this Apple-silicon Mac inclusion; Mac Development profile generation and download; inspection of profile UUID, team, application identifier, entitlements, devices and expiry; asserting the unsuffixed packet-tunnel-provider value on host and provider profiles alike; asserting the matrix negatives, namely that no App Groups capability is enabled on any of the four App IDs and that no generated profile Entitlements dict carries com.apple.security.application-groups (assertion A16). Out of scope: creating any App Group record; enabling the App Groups capability anywhere; any Keychain access-group portal mutation; provisioning the four deferred iOS identifiers; any Developer ID, App Store or other distribution profile; any change to the shipped legacy macOS bundle identity; committing profiles or certificates; TestFlight; notarization; unrelated capabilities; product code.

## Acceptance Criteria
1. Exactly four macOS App IDs exist under the expected Relux Works team - works.relux.tunnel.mac, works.relux.tunnel.mac.tunnel, works.relux.tunnel.probe.mac and works.relux.tunnel.probe.mac.tunnel - and match the approved naming matrix exactly; no App Group record is created; the four iOS identifiers stay defined in the matrix and are deliberately not provisioned because iOS is deferred under ADR-024. 2. The Network Extensions capability is enabled on all four App IDs, hosts included, and every generated Mac Development profile authorizes the unsuffixed packet-tunnel-provider value on host and provider profiles alike; the App Groups capability is enabled on none of the four; no Keychain access-group mutation is performed, and the team-wide keychain-access-groups wildcard that every Mac Development profile carries is expected and is not a finding. 3. One Mac Development profile per App ID is generated for this Apple-silicon Mac context, with the iPhone profile recorded as a named deferred gap under ADR-024, and each inspects to the expected team, application identifier, entitlements, devices and validity. 4. Reproduction steps and privacy-safe profile metadata are attached as a TASK-ID-scoped outcome resource; raw profiles, certificates and private keys are not attached or committed. 5. Any portal limitation or capability requiring Apple approval is recorded as an explicit external blocker rather than bypassed.
