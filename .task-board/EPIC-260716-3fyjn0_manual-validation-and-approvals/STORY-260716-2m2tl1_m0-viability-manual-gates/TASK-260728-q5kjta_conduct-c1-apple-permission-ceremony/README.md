# TASK-260728-q5kjta: conduct-c1-apple-permission-ceremony

## Description
THE single up-front human permission board node (Ceremony C1) on the current Apple-silicon Mac. This task exists so the board has exactly one human-input node for every up-front grant, instead of scattering grants across four tasks that a human would have to revisit across producer-reviewer cycles. Under the owner-approved 2026-08-10 ADR-028 amendment, the ceremony may contain honestly recorded resumed owner interactions with agent cycles between them; one continuous sitting and retrospective proof of historical UI clicks are not required. Every downstream evidence task (TASK-260715-apc34w, TASK-260715-3jloqy, TASK-260728-dveo1o, TASK-260717-ziprhs) then runs unattended using the access granted here. The human is never asked to wait through a review cycle. No secret value or secret path is ever requested, echoed, logged, screenshotted, committed, or stored on the board.

## Scope
In scope under the resumed-evidence amendment, within this one ceremony node: establishing effective prompt-free private-key access for the Apple Development and Developer ID Application identities to the signing tools that run unattended; confirming an authenticated Xcode or Apple Developer portal context for the Relux Works team and the exact macOS-only matrix authority, while honestly recording whether a separate two-factor timestamp exists and any later reauthentication risk; authorizing creation and download of exactly the macOS entries in the approved identifier and entitlement matrix (revision 2026-07-28.r12) and nothing beyond them, namely the four macOS App IDs works.relux.tunnel.mac, works.relux.tunnel.mac.tunnel, works.relux.tunnel.probe.mac and works.relux.tunnel.probe.mac.tunnel, the Network Extensions capability on those four and no other capability, and one Mac Development profile per App ID with this Apple-silicon Mac registered as a device; explicitly NOT creating any App Group record, NOT enabling the App Groups capability on any App ID, and NOT performing any Keychain access group mutation, because matrix rule G4 prohibits com.apple.security.application-groups on every macOS target, rule K2 prohibits keychain-access-groups on every macOS target, and keychain sharing has no portal record at all; storing a NAMED notarytool profile in the login Keychain; choosing and stating the owner disposition for the source App Store Connect API private-key file; generating the Sparkle ed25519 keypair with the pinned vendor tool and placing the private key into approved custody; recording only non-secret grant facts and honest provenance. Harmless command-name-only shell history is permitted, but secret values, secret-bearing arguments, identifiers, account credentials, key bytes, and secret paths are prohibited everywhere. Out of scope: approving any system VPN or system extension dialog (that is Approval A1 and later Hold H2, and no signed artifact exists yet); provisioning the deferred iOS identifiers; creating any Developer ID or App Store distribution profile; performing the portal mutations themselves (TASK-260715-3jloqy); validating profiles, verifying notary authentication, or recording public-key evidence (owned by the downstream evidence tasks); any product code; any owner product decision.

## Acceptance Criteria
1. Ceremony C1 remains exactly one up-front human-input board node. Evidence may be collected across resumed owner interactions with producer or reviewer cycles between them, provided the record gives every known interaction date or time, states which boundaries were not captured, identifies the intervening cycles, and makes no uninterrupted-session claim. The human is never asked to remain present through a producer or reviewer cycle. 2. Effective prompt-free private-key access is demonstrated for the Apple Development and Developer ID Application identities to the named unattended signing tools. The record names the identities by common name and the tools, never key material. Contemporaneous proof of the historical Always Allow click is not required; any provenance limitation is stated honestly. 3. An authenticated Xcode or Apple Developer portal context for the Relux Works team exists and the operator has confirmed authority to create the macOS entries in the approved matrix. A cached authenticated session is acceptable functional evidence without a separately timestamped two-factor event; the record states that limitation and any residual fresh-authentication or two-factor interaction the portal may force later. 4. Creation and download of exactly the approved macOS entries is authorized and nothing beyond them: the four macOS App IDs works.relux.tunnel.mac, works.relux.tunnel.mac.tunnel, works.relux.tunnel.probe.mac and works.relux.tunnel.probe.mac.tunnel; the Network Extensions capability on those four; and one Mac Development profile per App ID with this Mac registered. The record states explicitly that NO App Group record was created, that the App Groups capability was enabled on no App ID, that no Keychain access group portal mutation was performed or required, and that no Developer ID or App Store distribution profile was created. All FOUR iOS App IDs (works.relux.tunnel.ios, works.relux.tunnel.ios.tunnel, works.relux.tunnel.probe.ios, works.relux.tunnel.probe.ios.tunnel) are explicitly NOT authorized because iOS is deferred under ADR-024, and works.relux.proxy is not touched. 5. A NAMED notarytool credential profile is stored in the login Keychain and the owner states the disposition for the source App Store Connect API private-key file; only the profile name and the chosen disposition are recorded, never the file path, key ID, issuer ID, passphrase, or key bytes. 6. The Sparkle ed25519 keypair is generated with the pinned vendor tool and the private key is placed in approved custody; only the custody location name is recorded here. 7. Credential values and secret-bearing arguments are never echoed or recorded. A post-ceremony scan of the repository, board resources, run logs, and shell history finds no secret value, secret path, key ID, issuer ID, account credential, or key bytes. Harmless command-name-only history is permitted and must be reported honestly rather than suppressed from the evidence. 8. A TASK-ID-scoped outcome records which grants succeeded, which were declined, honest interaction provenance, and any residual interaction the portal may still force later; a declined grant is recorded as a named blocker on the specific downstream task rather than as an assumed grant.
