# Decide the macOS system-extension credential transport

## Description
Decide how one configured SSH profile's private key and optional passphrase reach the macOS packet-tunnel provider, given that the provider is a system extension running as root outside a user context. TASK-260715-ypo7yo established from Apple documentation and DTS guidance that the Data Protection Keychain is available only to code running in a user context and that keychain access groups share items between programs running as the SAME user. The macOS host runs as the logged-in user and the provider runs as root, so the .spec/security-privacy.md design (secrets in the Data Protection Keychain shared through one access group with the packet tunnel extension) cannot work on macOS as written. iOS is unaffected because its appex runs as the same user as its host. This task selects the macOS transport, states its security properties honestly, and defines the entitlement amendment it implies for the identifier matrix.

## Scope
In scope: the exact question the spec leaves open — by what mechanism does a root-context macOS NEPacketTunnelProvider obtain SSH private-key material and an optional passphrase that the user-context containing app holds, without placing secrets in providerConfiguration, App Group data, logs, or board resources; comparison of at least host-to-provider IPC seeding over NETunnelProviderSession/XPC, the file-based System keychain with an access group, and provider-owned root-context storage; on-demand and boot-time start behaviour when the containing app is not running; secret lifetime and zeroization implications; the resulting amendment (grant or keep prohibited) for keychain-access-groups on works.relux.tunnel.mac.tunnel in the TASK-260715-ypo7yo matrix; the entitlement and portal consequences of the selected option; a physical reachability check on this Apple-silicon Mac where one is needed to settle a documented uncertainty. Out of scope: implementing the vault or the resolver, iOS behaviour, host trust policy, key import or generation, engine selection, UI, and changing the identifier matrix directly — this task produces the amendment, TASK-260715-ypo7yo owns the matrix.

## Acceptance Criteria
1. The artifact states the exact open question verbatim and cites the two Apple-sourced facts that create it: a macOS NE system extension runs as root outside a user context, and the Data Protection Keychain plus keychain access groups only share items between programs running as the same user. 2. At least three candidate transports are compared on unattended/on-demand start with the containing app not running, secret lifetime and zeroization, blast radius if the provider is compromised, entitlement and portal cost, and testability; each candidate states what it CANNOT guarantee. 3. One transport is selected with rationale, or the task records a concrete blocker with options, tradeoffs, and a recommendation rather than a guessed design. 4. The selection produces an explicit amendment verdict for keychain-access-groups on works.relux.tunnel.mac.tunnel in the TASK-260715-ypo7yo matrix: either grant with the exact literal, or keep prohibited with the reason; the verdict names TASK-260715-ypo7yo as the applying owner. 5. Where documentation alone cannot settle reachability, a privacy-safe physical check on this Apple-silicon Mac records the observed result with commands and exit codes and no secret value; where no check was possible the limitation is named, never assumed away. 6. The affected downstream tasks TASK-260715-379cpk, TASK-260715-1o9wjz, TASK-260715-29ws8l, TASK-260715-2hhh7x, and TASK-260715-3f4lxy are listed with the specific assumption each must revise.
