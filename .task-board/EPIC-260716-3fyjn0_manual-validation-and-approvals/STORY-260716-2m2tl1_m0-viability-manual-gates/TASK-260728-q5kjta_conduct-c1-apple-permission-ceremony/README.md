# TASK-260728-q5kjta: conduct-c1-apple-permission-ceremony

## Description
THE single up-front human permission sitting (Ceremony C1) on the current Apple-silicon Mac. This task exists so the board has exactly one human-input node for every up-front grant, instead of scattering grants across four tasks that a human would have to revisit across producer-reviewer cycles. The human performs all grants in one session; every downstream evidence task (TASK-260715-apc34w, TASK-260715-3jloqy, TASK-260728-dveo1o, TASK-260717-ziprhs) then runs unattended using the access granted here. The human is never asked to wait for a review cycle. No secret value is ever requested, echoed, logged, screenshotted, committed, or stored on the board.

## Scope
In scope, all in one sitting: unlocking the login Keychain and granting always-allow private-key access for the Apple Development and Developer ID Application identities to the signing tools that run unattended; authenticating Xcode and the Apple Developer portal for the Relux Works team including two-factor; authorizing creation and download of exactly the macOS entries in the approved identifier and entitlement matrix (host App ID, packet-tunnel extension App ID, Network Extension packet-tunnel capability, App Group, Keychain access group, development profiles including this Mac as a registered device); running notarytool store-credentials interactively to write a NAMED profile into the login Keychain; choosing and stating the owner disposition for the source App Store Connect API private-key file; generating the Sparkle ed25519 keypair with the pinned vendor tool and placing the private key into approved custody; recording only non-secret grant facts. Out of scope: approving any system VPN or system extension dialog (that is Approval A1 and later Hold H2, and no signed artifact exists yet); provisioning the deferred iOS identifiers; performing the portal mutations themselves (TASK-260715-3jloqy); validating profiles, verifying notary authentication, or recording public-key evidence (owned by the downstream evidence tasks); any product code; any owner product decision.

## Acceptance Criteria
1. Every up-front grant is performed in ONE human session and the session record states the start and end time and that no producer or reviewer cycle occurred inside it. 2. The login Keychain is unlocked and always-allow private-key access is granted for the Apple Development and Developer ID Application identities to the named unattended signing tools; the record names the identities by common name and the tools granted, never key material. 3. An authenticated Xcode/Apple Developer portal session for the Relux Works team exists and the operator has confirmed authority to create the macOS entries in the approved matrix; two-factor is completed during this sitting. 4. Creation and download of exactly the approved macOS identifiers, capabilities, groups, and development profiles is authorized; the two iOS identifiers are explicitly NOT authorized because iOS is deferred under ADR-024. 5. A NAMED notarytool credential profile is stored in the login Keychain and the owner states the disposition for the source App Store Connect API private-key file; only the profile name and the chosen disposition are recorded, never the file path, key ID, issuer ID, passphrase, or key bytes. 6. The Sparkle ed25519 keypair is generated with the pinned vendor tool and the private key is placed in approved custody; only the custody location name is recorded here. 7. Shell history and command echo are suppressed for every credential command, and a post-ceremony scan of the repository, board resources, run logs, and shell history finds no secret value, key path, key ID, issuer ID, or account credential. 8. A TASK-ID-scoped outcome records which grants succeeded, which were declined, and any residual interaction the portal may still force later; a declined grant is recorded as a named blocker on the specific downstream task rather than as an assumed grant.
