# Select and record the macOS self-update mechanism

## Description
Produce the binding, primary-source-backed macOS self-update decision that refines ADR-018 and unblocks implementation. Select an exact reviewable Sparkle 2 release baseline and define the signed-appcast, already-notarized payload, channel, helper, sandbox/hardened-runtime, Network Extension replacement, rollback, key-custody, and supply-chain contract without generating secrets or implementing the updater.

## Scope
In scope: current official Sparkle documentation/releases and license; exact dependency/version baseline and update policy; EdDSA appcast verification; Developer ID/notarization ordering; stable and prerelease channels; feed hosting and cache rules; application/helper/XPC/sandbox/hardened-runtime integration boundaries; macOS packet-tunnel extension replacement/relaunch/reapproval caveats; rollback/downgrade/withdrawal/key-rotation behavior; privacy/telemetry posture; threat-model and CI downstream impacts; ADR/spec update, research report, task outcome, and reviewer evidence. Out of scope: creating the private EdDSA key, adding Sparkle code, signing/notarizing a build, publishing an appcast or GitHub release, physical update execution, final release cadence approval, iOS updates, or unsupported claims about OS approval behavior.

## Acceptance Criteria
1. A dated research report cites official Sparkle and Apple primary sources for the selected exact Sparkle 2 baseline, license, EdDSA/appcast requirements, helper/sandbox/hardened-runtime behavior, and update installation lifecycle; volatile facts are verified rather than recalled. 2. ADR-018 and the self-update spec record the exact framework/version policy, dependency integration shape, stable/prerelease channel/feed contract, and the invariant that every payload is an already-notarized Developer ID build before appcast publication. 3. The decision defines fail-closed signature/feed behavior, rollback/downgrade/withdrawal, key generation/custody/rotation/revocation boundaries, privacy/telemetry rules, and the exact human release gates without storing or generating any secret. 4. Network Extension replacement, host relaunch, system approval/reapproval uncertainty, helper/XPC, sandbox, and hardened-runtime claims are bounded to what primary evidence proves; physical clean-install/update validation remains an explicit later gate. 5. A TASK-ID-scoped outcome maps evidence to downstream TASK-260717-xempiv and TASK-260717-1mt4e7, records validation/privacy checks and residual gates, and a fresh independent Codex reviewer accepts the decision before done.
